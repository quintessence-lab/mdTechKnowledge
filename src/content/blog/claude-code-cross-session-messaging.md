> ## 要点
>
> - **独立セッション間の自律通信が可能になったのは v2.1.224（2026-08-07リリース）**。それ以前の `SendMessage` は、1つのセッションの内側にいるサブエージェントやチームメイト専用だった
> - **同一マシン内はAnthropicのサーバーを一切経由しない**。macOS/Linux はセッションごとのUnixドメインソケット、native Windows は名前付きパイプで直接配送される
> - **別マシン間・クラウドセッションはAnthropicサーバー経由**。相手側のRemote Control接続を通って届くため、Remote Controlの要件（claude.aiサインイン）を満たす必要がある
> - **他セッションからのメッセージはユーザーの承認にならない**。権限プロンプトへの代理回答も設定変更も禁止され、本文中のスラッシュコマンドは実行されずただのテキストとして届く
> - **native Windows の対応バージョンは情報源によって食い違う**。公式ドキュメントは v2.1.234、CHANGELOG は v2.1.239 の項目として告知している

---

## そもそも何が変わったのか

Claude Code には以前から `SendMessage` というツールがありました。ただし使える相手は限られていて、**自分が起動したサブエージェント**と、**自分のチームに属するチームメイト**だけでした。どちらも「1つのセッションの内側で生まれた存在」です。

つまり、ターミナルAで動いているセッションと、ターミナルBで動いているセッションは、互いの存在すら知りませんでした。片方が終わった結果をもう片方に伝えたければ、人間が読んでコピーして貼り付けるしかなかったわけです。

**v2.1.224 でこの壁が取り払われました。** 独立したセッション同士が `ListAgents` で互いを発見し、`SendMessage` で名前を指定して直接メッセージを送れるようになりました。しかも同一マシンに閉じず、自分の別のPCや、Claude Code on the web で動いているクラウドセッションにも届きます。

## 2つの経路 — どこを通って届くのか

相手がどこにいるかで、メッセージの通り道がまったく変わります。ここが本機能を理解する上で最も重要な点です。

| 相手のセッションの場所 | 経路 |
|:---|:---|
| **このマシン上** | macOS / Linux はセッションごとのUnixドメインソケット、native Windows はセッションごとの名前付きパイプ。**Anthropicのサーバーを一切経由しない** |
| **自分の別マシン上** | **Anthropicサーバー経由**で、そのマシンの **Remote Control** 接続を通って到達 |
| **Claude Code on the web 上** | **Anthropicサーバー経由**で、直接クラウドセッションへ |

同一マシン内が完全にローカル完結である点は、データの扱いを気にする環境では効いてきます。各セッションは自分自身をディスク上のファイルに登録し、Claude Code がそれを読んでローカルセッションを発見する仕組みです。

この「同じファイル群が見えるかどうか」が到達範囲を決めるため、次の組み合わせは**互いに到達できません**。

- **コンテナ内のセッションとホストのセッション** — ファイルシステムが別のため。ただし同一コンテナ内の2セッション同士は可能
- **WSL 2 内のセッションと native Windows のセッション** — ホームディレクトリが異なり、listen するソケットの種類も違うため

### 受信箱ソケットの確認方法

cross-session messaging が有効なセッションは、それぞれ受信箱（inbox）ソケットをバインドします。所在は2つの方法で確認できます。

- **`/status` の `Peer address` 行** — パスは `uds:` プレフィックス付きで表示される。セットアップに失敗している場合は `unavailable` と理由が出る
- **環境変数 `CLAUDE_CODE_MESSAGING_SOCKET`** — hooks と Bash コマンドにエクスポートされる。`SessionStart` を含むあらゆる hook の実行前にエクスポート済み

アクセス制御はプラットフォームで異なります。macOS / Linux はソケットを自分のOSユーザーに限定し、native Windows は接続ごとに「自分のOSユーザーだけが読める鍵」での認証を要求します。いずれにせよ、共有マシンで他ユーザーのセッションに配送されることはありません。

## `ListAgents` で見える5種類の相手

`/list-agents`（別名 `/peers`）で確認できます。出力の最初の行は、存在すれば**このセッション自身の名前**です。他のセッションがこのセッション宛に送るときに使う名前にあたります。

| 種別 | 内容 |
|:---|:---|
| **Subagents** | 現在のセッション内で動いているエージェント |
| **Teammates** | このセッション自身のエージェントチームのチームメイト |
| **ローカルの別セッション** | 同一マシン上のClaude Codeセッション（バックグラウンドセッション含む）。**受信箱ソケットをバインドしているものだけ**表示される |
| **クラウドセッション** | Claude Code on the web のセッション。ラベルは `cloud`。**このセッションがRemote Controlに接続している間だけ**見える |
| **別マシンのRemote Controlセッション** | ラベルは `Remote Control`。接続が切れているものは `offline` と表示 |

実際の出力は次のような形になります（Windows 11・v2.1.269 で確認、名前は一般化しています）。

```
This session is main-session [ffad0e] — the name other sessions use to message it.

Peer sessions (26):
  sub-session [1a281f]       ·  interactive     ·  idle  ·  started 2d ago
  remote-control-a [add623]  ·  cloud           ·  idle
  archived-session [0f926f]  ·  Remote Control  ·  offline
  ...
```

`interactive` / `cloud` / `Remote Control` という種別と、`busy` / `idle` / `offline` という状態が同時に読めます。**`offline` の相手にも送信自体は通り**、相手のマシンが再接続してから届きます。

### Remote Control接続中は情報が伏せられる

このセッションがRemote Controlに接続している間、`/list-agents` の出力からローカルセッションの一部の詳細が省かれます。

- **作業ディレクトリ** — 各ローカルセッションの作業ディレクトリを省く
- **セッション名** — 人に帰属できない名前は省き、名前のない行は `(unnamed session)` と表示
- **最初の行** — 起動時または最後のresume以降に、この端末で `--name` か `/rename` により自分でその名前を入力した場合を除き、自セッション名の行を省く

何かが列挙された場合は、出力末尾に詳細を伏せた旨の注記が付きます。

## 使い方

ユーザーが `ListAgents` や `SendMessage` を直接叩くことはありません。Claude が相手を発見して送ります。指示の出し方は自然文で構いません。

```
別のターミナルで動いているセッションに、マイグレーションが終わったか聞いて
```

```
@api-worker に、スキーマ移行が完了したと伝えて
```

`@` に続けてセッション名の先頭数文字を打つと typeahead から選べます（v2.1.232以降）。typeahead に出るのは**このマシン上の他のライブセッション**だけなので、クラウドや別マシンのセッションを指名したい場合は、先に Claude に一度列挙させる必要があります。名前にスペースなどが含まれる場合はダブルクォートで囲みます（例: `@"release notes"`）。

### 完了を待たずに通知を受け取る

`notify_when_idle` は、ポーリングせずに他セッションの完了を知るための仕組みです。

- 同一マシン上の自分のセッションに対し、**次にアイドルになるか終了したときに1回だけ**通知を返すよう購読する
- メッセージに付随させることも、単独で指定することもできる。**単独なら相手のターンを開始させず、トークンも消費しない**
- 両方のセッションで v2.1.236 以降が必要
- **12時間**以内に通知が来なければ購読は破棄される
- 購読できるのは**メインの会話のClaudeだけ**で、対象も**このマシン上のセッションだけ**。サブエージェントやチームメイトが指定した場合は購読が作られない

「終わった？」と繰り返し聞きに行くのではなく、相手から一度だけ知らせてもらう設計です。

## セキュリティ境界 — 他セッションは「ユーザー」ではない

ここが設計の肝です。セッションAからBにメッセージが届くと、Claude Code はBのClaudeに対して「これはユーザーからではなく別セッションからのメッセージである」と明示し、できることを制限します。

- **何も承認できない** — 他セッションからのメッセージは決してユーザーの同意にならない。保留中の権限プロンプトに代理で答えることはできない
- **設定を変更できない** — 他セッションに言われたからといって、権限設定や `CLAUDE.md` などを変更してはならないと指示される
- **コマンドは実行されない** — 本文中の `/compact` のような記述はプレーンテキストとして届き、実行されることはない
- **権限プロンプトは通常どおり出る** — メッセージに従って行動するのに権限が必要なら、普段の作業と同じプロンプトが表示される

送信側にも制約があります。Claude は「**自分のセッションで拒否された行為や、自分の権限設定がブロックする行為を他セッションに依頼してはならない**」と指示されています。他セッション経由で権限決定を迂回する、いわゆる権限ロンダリングを防ぐためです。ブロックされた作業はユーザーに戻されます。

また、受信側が受け取るのは**送信者の名前・返信先・本文テキストだけ**です。送信者の会話履歴やファイルが渡ることは決してありません。会話全体を引き継ぎたい場合は、メッセージではなくセッションのresumeを使います。

### マシン外への送信をすべて承認制にする

```json
{
  "isolatePeerMachines": true
}
```

`isolatePeerMachines` を `true` にすると、マシン外セッションへの `SendMessage` に明示的な承認が必須になります（`bypassPermissions` モードでも承認を求められる）。いずれかの設定スコープの `true` が適用されるため、**チェックインしたプロジェクトファイルで有効化はできるが無効化はできない**という非対称な挙動になっています。同一マシン内のメッセージには影響しません。

## 受信制御 — `crossSessionInbound`

| 値 | 挙動 |
|:---|:---|
| `accept` | 各メッセージをClaudeに配送する |
| `hold` | 通知だけ表示し、配送しない。後に `accept` が適用されるようになれば、保留していたメッセージを解放する |
| `refuse` | 配送せずに破棄する |

`/config` の「Messages from your other sessions」行から選択できます（v2.1.232以降）。なお **`/config crossSessionInbound=value` というショートハンドはこのキーでは拒否されます**。

### 既定値は「固定値ではない」

公式ドキュメントは、明示的なデフォルト値を定義していません。代わりに**両セッションの権限モードからメッセージごとに判断**します。

権限プロンプトをバイパスするセッションを1つのクラス、それ以外をもう1つのクラスとして分類します。ここで **auto・`acceptEdits`・`dontAsk` は「プロンプトする側」** に数えられ、**Plan mode は bypass permissions が利用可能なセッションでは「バイパスする側」** に数えられます。

- **受信側がプロンプトする側** → 各メッセージを配送する。送信側がバイパス側だと名乗った場合のみ承認のため保留
- **受信側がバイパスする側** → 各メッセージを承認のため保留する。送信側もバイパス側だと名乗った場合のみ配送

保留されると承認ダイアログが開き、`dialogExpiry`（既定**5分**）を過ぎて未応答ならダイアログを閉じてメッセージを破棄します。保留の上限は**100件**で、超えると古いものから捨てられます。

### 組織全体で無効化する

```json
{
  "permissions": {
    "deny": ["SendMessage", "ListAgents"]
  },
  "crossSessionInbound": "refuse"
}
```

受信を止めるだけなら `crossSessionInbound` を `refuse` に、送信と列挙も止めるなら `SendMessage` と `ListAgents` を deny ルールに追加します。ただし **`SendMessage` の deny はサブエージェントやチームメイトへのメッセージも同時に消える**点に注意が必要です。同じツールが両方を担っているためです。

## 制限事項

メッセージングチャネル自体の性質による制限で、どこで動かしても適用されます。

- **プレーンテキストのみ** — セッション間で渡せるのはテキストだけ。構造化されたエージェントチームのプロトコルメッセージはチーム内に留まる
- **同一マシン宛は約100万文字が上限** — シリアライズ後がこれを超えると送信側で拒否され、受信側には何も届かない
- **急激な連投は送信側で拒否** — 相手の受信箱の受け入れ限度に達すると、以後の送信が送信側で拒否される。残りを1つにまとめるか待つよう促される
- **メッセージループは自動で止まる** — 受信側が送信者ごとにレート制限し、短時間内の同一内容の繰り返しを破棄する。Claudeが読むために受け入れるメッセージは**最大50件**までキューされるため、2セッション間の往復は自然に停止する
- **bare mode のセッションは受信できない** — ソケットをバインドしないため、一覧にも出ない
- **クラウド・別マシンの一覧はページ数で打ち切られる** — 古いセッションは列挙されず、名前で送信できない

なお `claude -p` の非対話セッションも対話セッションと同様に受信箱をバインドするため、長時間稼働するワーカーもメッセージを受け取れます。

## native Windows の対応バージョンについて（情報源の食い違い）

本記事執筆時点で、**公式ドキュメントとCHANGELOGの記載が一致していません**。両方を記録しておきます。

**公式ドキュメント（cross-session-messaging）の記載**

> Cross-session messaging requires Claude Code v2.1.224 or later on macOS and Linux, including Linux inside WSL 2. On native Windows, it requires Claude Code v2.1.234 or later.

ドキュメント内で「2.1.234」が出てくるのは2箇所だけで、いずれも主語が "Cross-session messaging"（機能全体）です。一部のサブ機能に限定する記述はありません。また、ドキュメント内の「2.1.239」は listing にチームメイトや自セッション名が表示されるようになった話であり、**Windows対応とは結び付けられていません**。

**CHANGELOG v2.1.239 の記載**

> Windows: cross-session messaging is now available, so Claude Code sessions across your machines can message each other with `SendMessage` and find each other with `ListAgents`, as on macOS and Linux

CHANGELOG の v2.1.234 の項目にも Windows 関連の記載はありますが、NTネームスペースパスのセキュリティ修正と、読み取り専用の設定ファイルによる起動停止の修正であり、cross-session messaging とは無関係です。

**実用上の判断**: どちらが正しいかは公開情報からは確定できません。安全側に倒すなら **v2.1.239 以降**を前提にするのが無難です。いずれにせよ現行版（v2.1.269系）では問題なく動作します。

## 何に使うと効くのか

公式ドキュメントが挙げる用途と、実運用で効く場面を整理すると次のようになります。

| 場面 | 使い方 |
|:---|:---|
| **発見の引き継ぎ** | 破壊的変更や重要な決定を見つけたセッションが、その影響を受ける領域を作業中のセッションに要約して伝える |
| **並行worktreeの調整** | 別々のworktreeで同一リポジトリを扱うセッション同士で、何がマージされたかを共有する |
| **長時間処理の状況確認** | マイグレーションやテスト実行の進捗を報告させる。同一マシンなら `notify_when_idle` で完了時に1回だけ通知させる |
| **マシンを跨いだ連絡** | 別のPCや、web上で動いている自分のセッションに到達する |

逆に、**会話の続きをしたいだけなら resume** を使うべきです。メッセージで渡せるのはテキスト1通だけで、コンテキストは移りません。多数のセッションを俯瞰して操作したいなら agent view、スマホから自分で操作したいなら Remote Control が適切です。

---

## まとめ

- 独立セッション間の自律通信は **v2.1.224（2026-08-07）** から。それ以前の `SendMessage` はサブエージェント・チームメイト専用だった
- 2026年8月の1か月で、会話の開始（2.1.225）・`@`メンション（2.1.232）・アイドル通知（2.1.236）・Windows対応（2.1.239）・全プロバイダ対応（2.1.248）まで一気に整備された
- **同一マシン内はAnthropicサーバーを経由しない**ローカルソケット、**マシン外はRemote Control経由**という2つの経路がある
- 他セッションからのメッセージは**ユーザーの承認として扱われない**。権限の迂回は設計上ブロックされている
- コンテナ↔ホスト、WSL 2↔native Windows は互いに到達できない
